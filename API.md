# API проекта AI Engineer

Версия 0.2.0 от 17 ноября 2026 года. Лабораторная работа №4, вариант 3.

Этот документ описывает API для регистрации, входа и работы с протоколами испытаний робота. Оператор читает протоколы, Диагност проверяет их, Архитектор назначает роли участникам. Для демонстрации предусмотрен быстрый вход в подготовленные аккаунты.

Схемы запросов и ответов находятся в [openapi.yaml](./openapi.yaml). Реализация backend и демо-режим frontend должны возвращать одинаковые структуры данных и коды ошибок.

## Общие правила

Все маршруты начинаются с `/api`. Frontend отправляет запросы на тот же origin, на котором открыто приложение. При разработке Vite проксирует `/api` на backend. В Docker эту задачу выполняет веб-сервер frontend.

Тела запросов и ответов используют `application/json`. Ответ `204` приходит без тела. Даты передаются как `YYYY-MM-DD`, время как ISO 8601 в UTC. Пользователи получают постоянный UUID, протоколы — строковый ID вида `AE-041`.

Backend берёт пользователя из текущей сессии и проверяет его права перед каждой защищённой операцией. Данные о ролях в ответе помогают frontend показать доступные действия. Автором проверки протокола становится пользователь из сессии.

## Роли и права

| Код роли | Название | Права |
|---|---|---|
| `operator` | Оператор | `runs:read` |
| `diagnostician` | Диагност | `runs:read`, `runs:review` |
| `architect` | Архитектор | `runs:read`, `runs:review`, `roles:manage` |

У участника может быть несколько ролей. Его права складываются без повторов. Набор `[operator, diagnostician]` даёт чтение и проверку протоколов.

Новый аккаунт получает `operator`. Архитектор может заменить роли любого участника, в том числе свои и роли демопрофилей. Сервер проверяет полномочия по состоянию до изменения. Со следующего запроса действует обновлённый набор прав. Если Архитектор снимает с себя роль `architect`, frontend перечитывает `/api/me` и убирает управление ролями.

## Обзор маршрутов

| Метод и адрес | Действие | Доступ | Успех |
|---|---|---|---|
| `POST /api/register` | Создать аккаунт | Публичный | `201` |
| `POST /api/auth/login` | Войти по логину и паролю | Публичный | `200` |
| `POST /api/auth/demo` | Войти в демопрофиль | Учебный режим | `200` |
| `POST /api/auth/logout` | Выйти | Текущая сессия, если есть | `204` |
| `GET /api/me` | Получить свой профиль | Сессия | `200` |
| `GET /api/roles` | Получить матрицу ролей | Публичный | `200` |
| `GET /api/runs` | Получить список протоколов | `runs:read` | `200` |
| `GET /api/runs/{runId}` | Прочитать протокол | `runs:read` | `200` |
| `PATCH /api/runs/{runId}/review` | Проверить протокол | `runs:review` | `200` |
| `GET /api/users` | Получить участников | `roles:manage` | `200` |
| `PUT /api/users/{userId}/roles` | Назначить роли | `roles:manage` | `200` |

## Форматы данных

### Профиль пользователя

`User` содержит обязательные поля `id`, `login`, `roles` и `permissions`. Массив `permissions` сервер рассчитывает из текущих ролей. Здесь и далее значения в примерах служат образцами формата.

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "login": "pilot_04",
  "roles": ["operator"],
  "permissions": ["runs:read"]
}
```

### Строка списка протоколов

`RunSummary` содержит `id`, `title`, `robot`, `date` и `status`. По этим полям frontend строит журнал испытаний.

```json
{
  "id": "AE-041",
  "title": "Реакция на курсор",
  "robot": "AI Engineer",
  "date": "2026-11-04",
  "status": "pending"
}
```

### Полный протокол

`Run` включает все поля `RunSummary`, а также `summary`, `reviewedBy` и `reviewedAt`. До первой проверки последние два поля равны `null`. После проверки в них записываются логин проверяющего и время решения.

```json
{
  "id": "AE-041",
  "title": "Реакция на курсор",
  "robot": "AI Engineer",
  "date": "2026-11-04",
  "status": "approved",
  "summary": "Проверена реакция робота рядом с полями формы.",
  "reviewedBy": "diagnostics_01",
  "reviewedAt": "2026-11-04T15:20:00Z"
}
```

Статусы протокола — `pending` («На проверке»), `approved` («Принят») и `rejected` («На доработке»).

### Ошибка

Любая ошибка API содержит `code` и `message`. Если проблема относится к полю запроса, backend добавляет `fields`. Frontend определяет поведение по HTTP-статусу и `code`, а текст показывает пользователю.

```json
{
  "code": "LOGIN_TAKEN",
  "message": "Этот логин уже занят.",
  "fields": {"login": "Этот логин уже занят."}
}
```

## Регистрация и вход

### POST /api/register

Принимает только `login` и `password`.

```json
{"login": "pilot_04", "password": "Workshop!42"}
```

Логин содержит от 3 до 32 символов. Допустимы латинские буквы, цифры, точка, дефис и подчёркивание. Для отображения сервер сохраняет написание пользователя, для поиска и уникальности использует нижний регистр. `Pilot_04` и `pilot_04` считаются одним логином.

Пароль содержит минимум 8 кодовых точек Unicode, хотя бы одну заглавную и одну строчную букву, цифру `0–9` и символ из категории Unicode `P` или `S`. Пробел сам по себе требование спецсимвола не выполняет. Оба поля проверяются как переданы, без обрезки пробелов.

Успешный ответ `201` содержит `message` и `user` в формате `User`. Сервер назначает `operator` и открывает сессию. Frontend может сразу предложить переход в кабинет.

Ошибки — `409 LOGIN_TAKEN` для занятого логина и `422 VALIDATION_ERROR` для неверных полей, некорректного JSON или лишних свойств. Передача `roles` в регистрации также даёт `422`.

### POST /api/auth/login

Принимает `login` и `password`. Для логина действуют правила формата регистрации. Пароль при входе должен быть непустой строкой, затем backend сверяет его с сохранённым хэшем.

```json
{"login": "pilot_04", "password": "Workshop!42"}
```

Ответ `200` содержит `User` и устанавливает cookie сессии. При неверном логине или пароле сервер возвращает один ответ `401 INVALID_CREDENTIALS` с текстом «Неверный логин или пароль». Ошибки структуры запроса дают `422`.

### POST /api/auth/demo

Принимает код подготовленного профиля.

```json
{"profile": "diagnostics_01"}
```

| Профиль | Начальные роли |
|---|---|
| `operator_01` | `operator` |
| `diagnostics_01` | `diagnostician` |
| `architect_01` | `architect` |
| `student` | `operator` |

Backend заранее создаёт эти аккаунты вместе с демопротоколами. Маршрут открывает сессию выбранного аккаунта и возвращает `200` с `User`. После назначения новых ролей демовход возвращает сохранённые роли этого аккаунта.

Демовход доступен при `APP_ENV=development` или `APP_ENV=test` и `DEMO_AUTH_ENABLED=true`. По умолчанию флаг выключен. Выключенный маршрут и отсутствующий подготовленный аккаунт дают `404 NOT_FOUND`, неизвестный код профиля — `422 VALIDATION_ERROR`.

Для повторения защиты после изменения демоданных backend-разработчик предусматривает команду восстановления начальных данных учебного стенда и описывает её в README. Текущая кнопка сброса в HTML-макете очищает данные своего браузера.

### POST /api/auth/logout

Тело запроса отсутствует. Сервер отзывает текущую сессию, удаляет cookie и возвращает `204`. Повторный выход возвращает тот же статус.

### GET /api/me

Возвращает `200` с актуальным `User`. Frontend вызывает этот маршрут при запуске приложения, после изменения своих ролей и при возврате в открытую вкладку. Если сессия отсутствует или истекла, сервер отвечает `401 AUTH_REQUIRED`.

## Матрица и назначение ролей

### GET /api/roles

Доступен до входа. Возвращает массив всех трёх ролей. Каждый объект содержит `id`, `label`, `description` и `permissions`. Код `id` совпадает с кодом роли в профиле пользователя. Ниже приведён один элемент массива.

```json
{
  "id": "diagnostician",
  "label": "Диагност",
  "description": "Читает и проверяет протоколы испытаний.",
  "permissions": ["runs:read", "runs:review"]
}
```

### GET /api/users

Требует `roles:manage`. Возвращает `200` с массивом `User`, отсортированным по логину без учёта регистра. Frontend использует ответ для списка участников и проверки разрешённого или запрещённого доступа. У Оператора этот запрос получает `403 FORBIDDEN`.

### PUT /api/users/{userId}/roles

Требует `roles:manage`. `userId` — UUID участника из `/api/users`. Запрос полностью заменяет его набор ролей.

```json
{"roles": ["operator", "diagnostician"]}
```

В массиве должна быть хотя бы одна роль. Неизвестные коды, повторы, пустой массив, лишние поля и некорректный UUID дают `422`. Отсутствующий участник даёт `404`.

Ответ `200` содержит обновлённый `User`. Повтор того же набора ролей возвращает тот же результат. Изменение применяется одной транзакцией. При одновременных изменениях действует последний успешно сохранённый набор.

## Протоколы испытаний

### GET /api/runs

Требует `runs:read`. Возвращает `200` с массивом `RunSummary`. Порядок — сначала по `date` от новых к старым, затем по `id` по убыванию. Пустой список возвращается как `[]`.

### GET /api/runs/{runId}

Требует `runs:read`. Возвращает `200` с полным `Run`. Frontend запрашивает подробности при открытии записи из журнала. Если протокол отсутствует, ответ — `404 NOT_FOUND`.

### PATCH /api/runs/{runId}/review

Требует `runs:review`. Принимает решение по протоколу.

```json
{"status": "approved"}
```

Разрешены `approved` и `rejected`. Диагност или Архитектор может принять протокол либо вернуть его на доработку, а позже поменять решение. Сервер сохраняет новый статус, логин текущего пользователя в `reviewedBy` и текущее время UTC в `reviewedAt`.

Ответ `200` содержит полный `Run`. Повтор уже установленного статуса возвращает текущий протокол с прежними автором и временем. Изменение полей выполняется одной транзакцией. Если два проверяющих меняют решение одновременно, действует последнее успешно сохранённое изменение.

Отсутствующий протокол даёт `404`. Значение `pending`, неизвестный статус или лишние поля дают `422`. Проверка Оператором получает `403`.

## Сессия и обработка ошибок

Серверная сессия хранится по непрозрачному идентификатору. После регистрации, обычного входа или демовхода backend создаёт новую сессию и отзывает предыдущую сессию этого клиента. Ошибка входа сохраняет существующую сессию.

Cookie называется `ai_engineer_session`. Атрибуты — `HttpOnly`, `SameSite=Lax`, `Path=/api` и конечный срок жизни. При HTTPS добавляется `Secure`. На локальном HTTP атрибут `Secure` опускается. Cookie общая для вкладок одного origin. После выхода или смены профиля соседняя вкладка получает новое состояние при следующем запросе `/api/me`.

Для запросов `POST`, `PATCH` и `PUT` backend проверяет заголовок `Origin` по списку разрешённых адресов приложения. Отсутствующий или неподходящий `Origin` даёт `403 ORIGIN_NOT_ALLOWED`. В примерах curl этот заголовок указан явно. Ответы с данными сессии, участников и протоколов используют `Cache-Control: no-store`.

| HTTP | Код | Причина |
|---|---|---|
| `401` | `AUTH_REQUIRED` | Отсутствует действующая сессия |
| `401` | `INVALID_CREDENTIALS` | Неверный логин или пароль |
| `403` | `FORBIDDEN` | Не хватает права для действия |
| `403` | `ORIGIN_NOT_ALLOWED` | Источник изменяющего запроса не разрешён |
| `404` | `NOT_FOUND` | Нет объекта или маршрут демовхода выключен |
| `409` | `LOGIN_TAKEN` | Логин уже существует |
| `422` | `VALIDATION_ERROR` | Ошибка полей или структуры запроса |
| `500` | `INTERNAL_ERROR` | Внутренний сбой сервера |

Все операции могут вернуть `500` с общим сообщением об ошибке. Ответы `401` и `403` защищённых маршрутов следуют формату `Error`. Ошибки валидации FastAPI также приводятся к этому формату, с подсказками в `fields`.

Для регистрации backend использует Argon2id или bcrypt и уникальный индекс логина без учёта регистра. Пользователь и начальная роль сохраняются в одной транзакции. Ответы и структурированные логи содержат только разрешённые поля профиля, сведения об операции и ошибке. Пароль, его хэш и исходные значения полей из внутренних ошибок валидации исключаются из логов и ответов API.

## Примеры запросов

`BASE_URL` — адрес приложения, через который доступен `/api`. Cookie сохраняется во временный файл. В примерах используется вымышленный пароль.

```sh
BASE_URL=http://localhost:8080
session_file=$(mktemp)

curl -i -c "$session_file" "$BASE_URL/api/register" \
  -H "Origin: $BASE_URL" -H 'Content-Type: application/json' \
  -d '{"login":"pilot_04","password":"Workshop!42"}'

curl -i -b "$session_file" "$BASE_URL/api/me"
curl -i -b "$session_file" "$BASE_URL/api/runs"
curl -i -b "$session_file" "$BASE_URL/api/runs/AE-041"

# Под Оператором запрос возвращает 403.
curl -i -b "$session_file" "$BASE_URL/api/users"

# Включённый деморежим открывает кабинет Диагноста.
curl -i -b "$session_file" -c "$session_file" "$BASE_URL/api/auth/demo" \
  -H "Origin: $BASE_URL" -H 'Content-Type: application/json' \
  -d '{"profile":"diagnostics_01"}'

curl -i -b "$session_file" -X PATCH "$BASE_URL/api/runs/AE-041/review" \
  -H "Origin: $BASE_URL" -H 'Content-Type: application/json' \
  -d '{"status":"approved"}'

curl -i -b "$session_file" -c "$session_file" "$BASE_URL/api/auth/demo" \
  -H "Origin: $BASE_URL" -H 'Content-Type: application/json' \
  -d '{"profile":"architect_01"}'
curl -i -b "$session_file" "$BASE_URL/api/users"

# Подставьте UUID участника student из предыдущего ответа.
USER_ID=00000000-0000-0000-0000-000000000000
curl -i -b "$session_file" -X PUT "$BASE_URL/api/users/$USER_ID/roles" \
  -H "Origin: $BASE_URL" -H 'Content-Type: application/json' \
  -d '{"roles":["operator","diagnostician"]}'

curl -i -b "$session_file" -X POST "$BASE_URL/api/auth/logout" \
  -H "Origin: $BASE_URL"
rm -f "$session_file"
```

## Проверка перед подключением frontend

1. Регистрация создаёт Оператора и сессию. Слабый пароль даёт `422`, повтор логина с любым регистром — `409`.
2. После выхода обычный вход восстанавливает кабинет созданного аккаунта. Неверный пароль даёт `401`.
3. Матрица ролей доступна до входа. Защищённые запросы без сессии дают `401`.
4. Оператор читает список и полный протокол. Попытки проверки протокола и чтения участников дают `403`.
5. Диагност меняет решение по протоколу. Повтор того же решения сохраняет прежние `reviewedBy` и `reviewedAt`.
6. Архитектор назначает `student` две роли. Его следующий демовход возвращает объединение прав и позволяет проверить протокол.
7. Изменение ролей действует в уже открытой сессии. Повторное чтение `/api/me` возвращает новые права.
8. При выключенном демовходе `/api/auth/demo` даёт `404`. Восстановление учебных данных возвращает начальные аккаунты и протоколы.
